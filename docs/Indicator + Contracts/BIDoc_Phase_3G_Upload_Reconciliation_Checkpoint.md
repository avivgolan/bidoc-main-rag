# Phase 3G — התאמת מיפויים לאחר העלאת גרסת לוח חדשה

- תאריך: 2026-08-12
- סטטוס: מימוש מקומי ו־schema-only מרוחק הושלמו; שער ההחלה סגור; לא בוצעה כתיבת מיפוי או היסטוריה
- גבול: תצוגה מקדימה והמשך אוטומטי מבוקר בלבד; ללא חישובי לו״ז, יצירת התראות או חיבור צרכנים

## מה נוסף

Phase 3G מוסיף תזמור בבעלות השרת עבור המשכיות מיפוי בין שתי גרסאות לוח סמכותיות:

1. השרת מקבל מהדפדפן רק `sourceProjectId` של פרויקט MAIN.
2. השרת פותר בעצמו את מיפוי MAIN ל־KAPAIM וטוען את גרסת הלוח הנוכחית והקודמת.
3. ספירות גרסאות ומשימות ב־MAIN וספירת המיפויים ב־KAPAIM חייבות להתאים גם ל־`Content-Range` מדויק של PostgREST; ספירת המשימות נבדקת בנוסף מול `task_count` הסמכותי.
4. המיפוי הנוכחי מגיע רק מ־KAPAIM, והוכחת האישור מגיעה רק מהיסטוריית הביקורת הבלתי־ניתנת לשינוי.
5. `mappingDraft`, רשימות משימות, זהות סוקר, זמן ביקורת ופעולת `auto_continue` אינם מתקבלים מהדפדפן.
6. המשך אוטומטי מותר רק לפי כללי הזהות המדויקים הקיימים: UID יחיד, שם מנורמל זהה, רמת היררכיה זהה, ללא פעילות סיכום, ללא בעלות מתחרה ובביטחון של `0.95` לפחות.
7. ההחלה משתמשת רק ב־RPC האטומי הקיים `bidoc_contracts_review_activity_mapping_v1`.
8. מיגרציית guard קדמית שיושמה כ־schema-only עוטפת את אותו RPC בנעילה משותפת להחלטות ידניות ואוטומטיות; לכן החלטה ידנית שניצחה בין preview ל־apply אינה נדרסת.

## ממשקי השרת

- `POST /api/contracts/activity-mapping/reconciliation/preview` — קריאה בלבד.
- `POST /api/contracts/activity-mapping/reconciliation/apply` — דורש שער שרת נפרד ומדויק:

```text
CONTRACTS_PHASE3G_UPLOAD_RECONCILIATION_APPROVED=TRUE
```

שני הממשקים מקבלים גוף זה בלבד:

```json
{
  "sourceProjectId": "<MAIN project UUID>"
}
```

## הגנות כשל סגור

הפעולה נעצרת לפני כל כתיבה כאשר:

- אין גרסה קודמת אחת וברורה;
- לגרסה הנוכחית או הקודמת אין `relevancy_date` תקין, או שהתאריך אינו מתקדם;
- הגרסה הנוכחית או הקודמת עמומה;
- ספירת `Content-Range` של גרסאות, משימות או מיפויים חסרה או אינה תואמת למספר השורות שנטען;
- שורת גרסת MAIN חסרה `file_id`, אינה שייכת ל־`sourceProjectId`, חסרה תאריך `relevancy_date` סמכותי ותקין, או חוזרת על `file_id` שכבר נטען;
- `task_count` אינו תואם למספר המשימות שנטען;
- UID מופיע יותר מפעם אחת;
- UID אחר חולק עם יעד ההמשך את אותו שם מנורמל ואותה רמת היררכיה;
- מיפוי מאושר אינו מגובה באירוע היסטוריה יחיד התואם למזהה שורת המיפוי, זמן האישור והגרסה;
- חסר קשר חוזי מאושר לאותו מפתח קנוני;
- קיימת בעלות קנונית מתחרה או תוצאת התאמה אחרת שאינה חד־משמעית.

מפתח האירוע נגזר באופן דטרמיניסטי מכל זהויות המקור. ריצה חוזרת מזהה מיפוי נוכחי שכבר מגובה בהיסטוריה ואינה כותבת שוב. מיפוי נוכחי שאושר ידנית נשמר ואינו מוחלף ב־`auto_confirmed`. ה־forward migration היא `20260812194500_contracts_phase3g_auto_continuation_manual_guard.sql`; rollback לא־הרסני מחזיר את מימוש ה־RPC הקודם בלי למחוק מיפויים או אירועי היסטוריה.

- KAPAIM מתעד את מיגרציית קריאת ההיסטוריה של Phase 3F כ־`20260812200241` ואת מיגרציית ה־guard של Phase 3G כ־`20260812200652`.
- בדיקת קטלוג האבטחה עברה: הפונקציות הן `SECURITY INVOKER`, עם `search_path` ריק והרשאת `EXECUTE` ל־`service_role` בלבד.
- לפני ואחרי ההחלה נשארו `0` שורות ב־`schedule_activity_map` ו־`0` אירועי ביקורת ב־`private.schedule_activity_mapping_review_events`.
- השרת הופעל מחדש כ־PID `60996`, עם Phase 3F.1 פעיל ועם `CONTRACTS_PHASE3G_UPLOAD_RECONCILIATION_APPROVED` סגור.
- preview חי וקריאה בלבד עבור MAIN `652bf3e0-9a1e-47ca-b06f-cd8dc33907f7` נכשל סגור כמצופה: HTTP `409`, קוד `contracts_activity_mapping_reconciliation_previous_version_missing`.
- נתיב apply הוכיח את שער השרת הסגור לפני קריאת מקור או כתיבה: HTTP `503`, קוד `contracts_activity_mapping_reconciliation_apply_not_approved`.
- לא נוצרו מיפוי, אירוע היסטוריה, שורת Schedule או התראה כתוצאה מן ההחלה או מן האימות החי.

## מה עדיין נדרש לתעודת יציאה מ־Phase 3

המימוש המקומי, ה־schema-only המרוחק ובדיקות הכשל הסגור עדיין אינם מוכיחים המשכיות בין שתי העלאות אמיתיות. בדיקת היציאה דורשת בנפרד:

1. הדרישה הבאה המדויקת היא להעלות ל־MAIN גרסת לוח שנייה, אמיתית, מתוארכת ומובחנת עבור אותו פרויקט.
2. לאחר ההעלאה יש להריץ שוב preview קריאה בלבד ולבדוק את כל החסמים והתוצאות ללא כתיבה.
3. אין לייצר מיפוי מלאכותי עבור הדוגמה שנדחתה; המשך אוטומטי אפשרי רק עבור מיפוי חוזי אמיתי ומאושר שמגובה בהיסטוריה בלתי־ניתנת לשינוי.
4. אין להריץ apply חי או לפתוח את שער Phase 3G ללא אישור נפרד ומפורש לאחר בדיקת ה־preview.
5. לאחר apply מאושר עתידי יש לאמת ריצה חוזרת ללא שורה או אירוע כפולים.

לאחר נקודה זו יש לעצור לפני חיבור צרכן Schedule, חישובי Engine, כתיבת התראות או Phase 4.
